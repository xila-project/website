Xila guest applications are sandboxed WebAssembly modules compiled for the `wasm32-wasip1` target and linked against the `xila-wasm` crate (`wasm` library name). At runtime, the host [`wasm` executable](/reference/wasm-runtime/) executes the module inside the `wasmi` interpreter and exposes two host-import namespaces:

- `wasi_snapshot_preview1` — standard WASI Preview 1 system calls for file I/O, directory traversal, environment variables, clocks, random bytes, cooperative yielding, and Xila's custom [`fd_control`](#vfs-device-control-fd_control) character-device extension (<CodeReference repo="applications" path="executables/wasm/src/guest/wasi.rs" />).
- `xila` — the multiplexer import `xila_graphics_call(function_id: u16, payload_ptr: usize) -> i32`, wrapped by safe Rust functions and types in <GuestReference repo="applications" crate="wasm" /> (<CodeReference repo="applications" path="executables/wasm/src/guest/graphics/mod.rs" />).

## Guest application structure and lifecycle

### 1. Entrypoint and CLI arguments

A Xila WebAssembly guest is a standard Rust binary crate compiled with `cargo build --target wasm32-wasip1`. The Rust standard library's `wasm32-wasip1` runtime exports `_start: () -> ()`, which invokes `fn main()` and converts any returned `Result::Err` or panic into `proc_exit`.

When the host launches `/bin/wasm <wasm_file> -- <args...>`, the host runtime (<CodeReference repo="applications" path="executables/wasm/src/host/main.rs" />) strips the host flags and forwards the guest binary path plus trailing arguments through `args_sizes_get` and `args_get` (`std::env::args()`).

### 2. Per-application VFS directories and environment variables

Before instantiating the guest module, [`VirtualMachine::new`](/reference/wasm-runtime/#command-syntax) derives the application identifier from the `.wasm` filename stem (for example, `calculator.wasm` -> `calculator`), resolves the active user via `users::get_user_name`, and creates three application directories in the Virtual File System (<CodeReference repo="applications" path="executables/wasm/src/host/execution.rs" />):

| Environment variable             | Provisioned VFS path                                 | Purpose                                             |
| :------------------------------- | :--------------------------------------------------- | :-------------------------------------------------- |
| `XILA_APPLICATION_CONFIGURATION` | `/users/<username>/applications/<app>/configuration` | Persistent per-user configuration files.            |
| `XILA_APPLICATION_DATA`          | `/users/<username>/applications/<app>/data`          | Persistent per-user application data and documents. |
| `XILA_APPLICATION_CACHE`         | `/users/<username>/applications/<app>/cache`         | Disposable per-user runtime cache.                  |

Guest code reads these paths with `std::env::var("XILA_APPLICATION_DATA")` and opens files inside them using `std::fs::File`.

### 3. Application bundle layout (`.xap`)

When packaged for the Xila package manager or installed into the rootfs via `build_Shortcut_Package`, an application bundle contains the compiled `.wasm` binary and a `shortcut.json` manifest (<CodeReference repo="applications" path="executables/calculator/shortcut.json" />):

```json
{
  "name": "Calculator",
  "command": "/bin/wasm",
  "arguments": ["{application_folder_path}/calculator.wasm"],
  "terminal": false,
  "icon_string": "±",
  "icon_color": [40, 120, 210]
}
```

## Graphical event loop and window lifecycle

Guest graphical applications follow a poll-and-sleep event loop driven by the guest thread (<CodeReference repo="applications" path="executables/calculator/src/interface.rs" />, <CodeReference repo="applications" path="executables/pixel_painter/src/interface.rs" />):

1. **Create the root window** with <GuestReference repo="applications" crate="wasm" kind="fn" symbol="window_create" /> and configure its taskbar icon using <GuestReference repo="applications" crate="wasm" kind="fn" symbol="window_set_icon" /> and <GuestReference repo="applications" crate="wasm" kind="struct" symbol="Color" />.
2. **Build the widget tree** by passing the window (or a container widget) as the `parent: u16` handle to constructors such as <GuestReference repo="applications" crate="wasm" kind="fn" symbol="object_create" />, <GuestReference repo="applications" crate="wasm" kind="fn" symbol="label_create" />, <GuestReference repo="applications" crate="wasm" kind="fn" symbol="button_create" />, or <GuestReference repo="applications" crate="wasm" kind="fn" symbol="buttonmatrix_create" />.
3. **Poll window events** in a loop using <GuestReference repo="applications" crate="wasm" kind="fn" symbol="window_pop_event" /> (or <GuestReference repo="applications" crate="wasm" kind="fn" symbol="window_pop_pointer_event" /> when reading pointer coordinates `(x, y)` on an <GuestReference repo="applications" crate="wasm" kind="fn" symbol="indexed_canvas_create" /> surface).
4. **Yield cooperatively when idle**: When the window's 32-slot event queue is empty, `window_pop_event` succeeds and returns `code == EventCode::All` (<GuestReference repo="applications" crate="wasm" kind="enum" symbol="EventCode" />). The guest calls `std::thread::sleep(Duration::from_millis(20))` (which invokes WASI `poll_oneoff` on the host) so the host graphics task and other virtual machines can run.
5. **Exit on window close**: When the user closes the window, the host pushes <GuestReference repo="applications" crate="wasm" kind="constant" symbol="EVENT_CLOSE_REQUESTED" /> (`EventCode::Cancel`, raw value `24`). Breaking out of the loop and returning from `main()` drops the VM instance, and the host automatically destroys all remaining widgets and the window (<CodeReference repo="applications" path="executables/wasm/src/host/graphics/objects.rs" />).

### Minimal graphical guest example

```rust
use std::{thread::sleep, time::Duration};
use wasm::{
    Color, EVENT_CLOSE_REQUESTED, EventCode, FlexAlign, FlexFlow, button_create, label_create,
    label_set_text, object_set_flex_align, object_set_flex_flow, window_create, window_pop_event,
    window_set_icon,
};

fn main() -> Result<(), String> {
    let window = window_create().map_err(|e| format!("Failed to create window: {e:?}"))?;
    window_set_icon(window, "+", Color::new(40, 120, 210))
        .map_err(|e| format!("Failed to set window icon: {e:?}"))?;

    object_set_flex_flow(window, FlexFlow::Column)
        .map_err(|e| format!("Failed to set flex flow: {e:?}"))?;
    object_set_flex_align(
        window,
        FlexAlign::Center,
        FlexAlign::Center,
        FlexAlign::Center,
    )
    .map_err(|e| format!("Failed to set flex align: {e:?}"))?;

    let button = button_create(window).map_err(|e| format!("Failed to create button: {e:?}"))?;
    let label = label_create(button).map_err(|e| format!("Failed to create label: {e:?}"))?;
    label_set_text(label, "Click me").map_err(|e| format!("Failed to set text: {e:?}"))?;

    let mut clicks = 0u32;
    loop {
        let (code, target) =
            window_pop_event(window).map_err(|e| format!("Failed to pop event: {e:?}"))?;

        if code == EVENT_CLOSE_REQUESTED {
            break;
        }
        if code == EventCode::All {
            sleep(Duration::from_millis(20));
            continue;
        }
        if code == EventCode::Clicked && target == button {
            clicks += 1;
            let text = format!("Clicked {clicks} times");
            label_set_text(label, &text).map_err(|e| format!("Failed to update label: {e:?}"))?;
        }
    }

    Ok(())
}
```

## Graphics API surface (`xila::xila_graphics_call`)

All graphical operations in <GuestReference repo="applications" crate="wasm" /> serialize a `#[repr(C)]` request struct on the guest stack and call <GuestReference repo="applications" crate="wasm" kind="fn" symbol="xila_graphics_call" /> (`(function_id: u16, payload_ptr: usize) -> i32`). Negative return codes map to <GuestReference repo="applications" crate="wasm" kind="type" symbol="Error" /> (<GuestReference repo="applications" crate="wasm" kind="enum" symbol="LvglResult" />), while non-negative return values carry object handles (<GuestReference repo="applications" crate="wasm" kind="type" symbol="ObjectHandle" />), booleans, or scalar measurements.

For the binary ABI layout, per-VM resource limits (up to **256** object handles per VM without slot reuse, 32 queued events per window), and numeric status codes, see the [Graphics Bindings ABI Reference](/reference/graphics-bindings/).

### VFS device control (`fd_control`)

In addition to standard WASI calls, Xila exposes `wasi_snapshot_preview1::fd_control` and its safe guest wrapper <GuestReference repo="applications" crate="wasm" kind="fn" symbol="fd_control" /> (<CodeReference repo="applications" path="executables/wasm/src/guest/wasi.rs" />) so guest applications can issue typed `Control_Command_Identifier` requests to VFS character devices such as `/devices/audio/playback`:

```rust
pub fn fd_control(
    file_descriptor: i32,
    command: u32,
    input: &[u8],
    output: &mut [u8],
) -> Result<(), u16>
```

The host handler (<CodeReference repo="applications" path="executables/wasm/src/host/wasi/file.rs" />) enforces four safety invariants on every `fd_control` invocation:

1. **Write-capability check**: Commands whose write-direction bit is set (`(command & 0x4000_0000) != 0`) require the descriptor to have been opened with write access (`OpenOptions::new().write(true)`), returning `__WASI_ERRNO_BADF` (`8`) otherwise.
2. **Payload size bound**: Neither `input.len()` nor `output.len()` may exceed **256 bytes** (`Control_Buffer_Data::MAX_CAPACITY`); larger slices fail with `__WASI_ERRNO_INVAL` (`28`).
3. **16-byte guest alignment**: When `input` or `output` is non-empty, its guest pointer must be 16-byte aligned (`ptr % 16 == 0`) to match `Control_Buffer_Data`'s alignment (`#[repr(C, align(16))]`). Use a `#[repr(C, align(16))]` wrapper buffer on the guest stack (<CodeReference repo="applications" path="executables/synth/src/device.rs" />).
4. **Non-overlapping buffers**: When both `input` and `output` are non-empty, their byte ranges in guest linear memory must not overlap (`__WASI_ERRNO_INVAL`).

## Runtime constraints and local documentation build

- **Cooperative fuel slicing**: The host executes guest bytecode in slices of `--instruction-limit` (default `100_000` `wasmi` fuel units) before yielding to the async executor (<CodeReference repo="applications" path="executables/wasm/src/host/execution.rs" />). Avoid busy-wait spin loops; always sleep via `std::thread::sleep` when waiting for UI events or audio buffers.
- **Monotonic object handles**: Each VM instance can allocate up to **256** graphics handles (`MAX_OBJECTS = 256`). Calling <GuestReference repo="applications" crate="wasm" kind="fn" symbol="object_delete" /> frees the underlying LVGL widget and clears the table entry, but handle indices are not recycled within the same VM run (<CodeReference repo="applications" path="executables/wasm/src/host/graphics/objects.rs" />). Reuse persistent widgets (by updating text or toggling `ObjectFlag::Hidden`) rather than repeatedly creating and deleting transient widgets in a loop.
- **Generating Guest Rustdoc locally**:

```bash
# From the applications repository:
RUSTDOCFLAGS="--deny warnings" mise run docs:guest

# Or directly with cargo:
cargo doc --package xila-wasm --no-default-features --features default_guest --target wasm32-wasip1 --no-deps
```
