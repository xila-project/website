The Wasm executable loads WebAssembly (Wasm) guest applications from Xila's virtual file system (VFS) and executes them using the <DocsRsReference crate="wasmi" /> interpreter. The `xila-wasm` crate in the Applications repository provides both the host runtime program and the guest API helpers.

## Context

Xila applications run as sandboxed WebAssembly modules rather than native machine code. This architecture isolates application memory from the kernel, provides a uniform binary format across host CPU architectures, and enables applications to run identically on microcontroller development boards, desktop native builds, and browser platforms.

The host executable mounts at `/applications/executables/wasm` in the VFS. It depends on Core subsystems (<HostReference crate="virtual_file_system" kind="struct" symbol="VirtualFileSystem" />, <HostReference crate="task" kind="struct" symbol="Manager" />, and <HostReference crate="graphics" kind="struct" symbol="Manager" />) and implements <HostReference crate="executable" kind="trait" symbol="ExecutableTrait" /> to integrate into Xila's process lifecycle.

## How it works

### System call pathway

The following diagram shows how a guest call reaches a device driver or display hardware.

```mermaid
flowchart LR
    Guest["Guest application (wasm32-wasip1)"] --> Import["Host import (WASI or graphics)"]
    Import --> HostRuntime["Host runtime (xila-wasm)"]
    HostRuntime --> Subsystem["VFS or graphics subsystem"]
    Subsystem --> Driver["Device driver or display hardware"]
```

The guest application executes within sandboxed WebAssembly linear memory and invokes an imported host function. System calls enter through `wasi_snapshot_preview1` for standard I/O, or through `xila_graphics_call` for graphical operations. The host runtime verifies memory bounds, checks task capabilities, and forwards requests to Core subsystems. The subsystems then dispatch typed control commands or pixel operations to underlying device drivers.

### Module initialization and lifecycle

When launched from the shell or desktop, the host runner completes the following lifecycle:

1. Path resolution: The runner reads the module bytecode from the VFS into memory using <CodeReference repo="applications" path="executables/wasm/src/host/main.rs" />.
2. Directory provisioning: If the path belongs to an application bundle, the runner ensures configuration, data, and cache directories exist for the calling user, configuring `XILA_APPLICATION_*` environment variables.
3. Engine instantiation: A fresh Wasmi engine and store are allocated for each execution. There is no globally cached interpreter state.
4. Eager translation: Function bytecode is translated eagerly before execution begins, ensuring that fuel exhaustion cannot interrupt lazy compilation.
5. WASI environment setup: Standard streams (`stdin`, `stdout`, `stderr`) are mapped to descriptors `0`, `1`, and `2`. If available, the root directory (`/`) is preopened as descriptor `3`.
6. Import registration and execution: WASI and graphics imports are linked, and the runner invokes the exported entry point `_start: () -> ()`.
7. Teardown: On exit or trap, the runtime cleans up allocated resources and frees all VM-owned graphics objects.

### Cooperative fuel slicing

Xila operates on an asynchronous cooperative multitasking model. To prevent a guest module from monopolizing CPU execution, the host configures Wasmi fuel metering:

- Each execution slice consumes fuel up to `--instruction-limit` (defaulting to 100,000 instructions).
- When fuel is exhausted, Wasmi suspends execution.
- The host runtime yields control to Xila's task scheduler, allowing other system tasks and display updates to run.
- When the task resumes, fuel is replenished and execution continues.

### Host and guest architectural boundary

Xila maintains a strict separation between guest code and the host environment:

- Guest applications compile to `wasm32-wasip1`. They interact solely through WASI system calls and the safe guest API.
- The browser runtime compiles Xila's host kernel and drivers to `wasm32-unknown-unknown`. In this mode, the browser runs the Xila host, which in turn executes `wasm32-wasip1` guest applications within Wasmi.

## Design choices and trade-offs

- Eager compilation: Translating all functions at module load time increases startup latency slightly, but eliminates the risk of compilation failures during time-critical event processing or when fuel is nearly exhausted.
- Isolated engine per execution: Creating a distinct Wasmi engine and store per guest run prevents state leakage between executions and ensures that memory corruption or crashes in one application cannot affect another.
- Monotonic descriptor tables: Descriptors within a guest execution are allocated monotonically, avoiding use-after-free bugs from reused descriptor numbers.

## Limits

- Scheduling quantum: Execution slices are metered by instruction count, not wall-clock time; CPU-intensive instructions may vary in duration.
- Polling support: The `poll_oneoff` WASI implementation supports clock timer subscriptions, but does not support arbitrary file descriptor readiness events.
- Single root preopen: Guests receive descriptor `3` preopened to `/`; path operations resolving outside `/` are rejected with `Notcapable`.
