The Platforms `drivers_espressif` crate contains Espressif-specific source, including pin mappings for the ESP32 family chips.

## Context

This source is separate from the native and browser runtime drivers. Its crate is gated on the `espressif` target vendor.

## How it works

The chip source lists GPIO pin numbers and delegates mounting to shared pin code. The crate is gated out on host targets, so host builds do not exercise that code.

The shared Espressif firmware mounts the GPIO controller on both WT32-SC01 boards. Each pin of the user connectors appears as `/devices/gpio/pin<number>`. The firmware withholds every pin that the board itself uses, so a device cannot reconfigure the display, touch panel, console, flash, microSD slot or RS-485 transceiver. The board READMEs list the exposed pins.

On the WT32-SC01 Plus, a microSD card in the slot appears as the block device `/devices/storage/sd_card`. A card that holds LittleFS is mounted at `/media/sd_card`. The firmware never formats a card by itself: a root shell writes `erase` to `/configuration/system/format_sd_card` and reboots to format the card, or writes `test` to `/configuration/system/test_sd_card` to run a write and read-back test at the next boot.

## Design choices and trade-offs

Target gating allows host builds to exclude the Espressif source. A successful host build therefore does not prove that an ESP32 runtime builds.

## Limits

The crate stays gated out on host targets, so host builds do not prove that an Espressif runtime builds. Platforms CI builds the WT32-SC01, WT32-SC01 Plus and ESP32-P4 Function EV Board firmware, and boots the ESP32-S3 and ESP32-C6 images in Espressif's QEMU.
