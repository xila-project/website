The `debug_protocol` crate defines typed data contracts, validation rules, and protocol bounds for Xila's headless diagnostics and automation interface. It lives in the Core repository under `libraries/debug_protocol/` and is published as the `xila-debug-protocol` package.

## Context

Test runners, diagnostic tools, and automation clients such as `xila-debug` inspect system state, capture framebuffers, and simulate user input. They need a consistent, portable protocol. The `debug_protocol` library defines this wire format independently of the network and transport layers. Headless testing then works across desktop environments, continuous integration pipelines, and embedded targets.

## How it works

### Request model and wire format

Requests are modeled by the <Api path="debug_protocol::Request" /> enum and serialized as JSON with `#[serde(tag = "op", rename_all = "snake_case")]`. The supported operations include:

- `Diagnostics`: Query runtime diagnostic statistics.
- `Capabilities`: Query supported driver capabilities.
- `Click { role, name, text, button }`: Hit-test and click a visible UI widget matching selector fields.
- `PointerClick { x, y }`: Click directly at the specified coordinates.
- `Resolution`: Query display dimensions.
- `Screenshot { path }`: Request screenshot save to a destination path.
- `UiTree { max_elements, max_depth }`: Query snapshot of the LVGL widget hierarchy. Defaults are 64 elements and 16 levels.
- `PointerMove { x, y }`: Move the mouse pointer to coordinates.
- `PointerButton { state: InputState }`: Set button state to `Pressed` or `Released`.
- `Key { key, state: InputState }`: Send key press or release events.
- `PressKey { key }`: Queue an atomic key press followed immediately by release.
- `Text { text }`: Inject a text string.

Example serialized request:

```json
{
  "op": "click",
  "name": "Login"
}
```

### Protocol constants and limits

The crate defines explicit upper bounds for all incoming and outgoing frames:

- `MAX_REQUEST_BYTES`: 16 KiB (16,384 bytes) for encoded request payloads.
- `MAX_TEXT_BYTES`: 4 KiB (4,096 bytes) for text injection strings.
- `MAX_RESPONSE_BYTES`: 64 KiB (65,536 bytes) for diagnostic responses.
- `MAX_SCREENSHOT_PIXELS`: 2,073,600 pixels (for example 1920×1080 resolution).
- `MAX_SCREENSHOT_BYTES`: 8,294,400 bytes (RGBA8888, 4 bytes per pixel).
- `DEFAULT_UI_TREE_ELEMENTS`: 64 elements maximum by default.
- `DEFAULT_UI_TREE_DEPTH`: 16 levels maximum depth by default.

### Frame validation

Validation functions reject malformed or oversized payloads before execution:

- <Api path="debug_protocol::validate_request" />: Ensure injected text does not
  exceed `MAX_TEXT_BYTES` and screenshot paths are non-empty. For `Click`
  requests, verify that at least one selector field is present. Reject any
  selector string that is empty or exceeds 512 bytes.
- <Api path="debug_protocol::validate_screenshot_metadata" />
  : Take a
  <Api path="debug_protocol::ScreenshotMetadata" />
  record. Ensure width and height are non-zero. Verify that `payload_bytes`
  equals `width * height * 4`. Check that the size does not exceed
  `MAX_SCREENSHOT_BYTES`.

Failures return <Api path="debug_protocol::ProtocolError" />. The `code()` method produces stable string error identifiers (such as `invalid_selector`, `text_too_large`, `empty_screenshot_path`, and `invalid_screenshot_frame`).

The client sends a serialized JSON request. The receiving device runs `validate_request` to check bounds and selectors. The device then forwards the command to the graphics subsystem, executes the UI interaction, and sends a JSON response to the client.

## Design choices and trade-offs

- Sans-I/O architecture: Protocol validation and message structures are decoupled from transport sockets, pipes, and serial connections.
- Strict resource bounds: Limits on buffer sizes and screenshot dimensions guard against denial-of-service and memory exhaustion on memory-constrained devices.
- JSON wire format: External scripts can inspect and debug the traffic without custom binary decoders.

## Limits

- Screenshots currently support only `ScreenshotPixelFormat::Rgba8888`.
- Transports must enforce `MAX_REQUEST_BYTES` and `MAX_RESPONSE_BYTES` during read and write loops; the protocol crate only validates structured fields.
