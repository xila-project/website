This guide shows how to submit a released package to the registry.

## Before you begin

- Build a signed package and retain its developer public key. See [Package an application](/how-to/package-application/).
- Publish the `.xpk` at an HTTPS release URL and install the <CodeReference repo="package_manager" path="crates/builder">desktop tool</CodeReference>.
- Obtain a checkout of the [registry repository](https://github.com/xila-project/registry) and access to open a pull request.

## Steps

1. In a host shell in the registry repository root, generate the entry using your package, public key, publisher ID and release URL:

   ```sh
   xila-package registry entry ./Weather.xpk ./public.key example-developer https://xila.example/Weather.xpk packages/example/xila/weather/1.0.0.json
   ```

2. If this is the publisher's first contribution, add its developer-key JSON under `keys/developers/`. The key must authorize the package identifier through a namespace file under `namespaces/` or the legacy `xila.<name>` grant, and the package kind through its `kinds`. Follow the <CodeReference repo="package_manager" path="schemas/developer-key.schema.json">developer-key schema</CodeReference>.
3. In a host shell in the registry repository root, validate the checkout:

   ```sh
   bash tools/validate.sh
   ```

4. Open a pull request adding the entry and, if needed, the developer key. Published version entries cannot be modified or deleted. Submit a new version instead. The `tools/check_immutable.sh` check enforces this.

You usually submit through the **Submit a package** issue form of the registry repository; the steps above describe the same submission done by hand. The submission workflow runs when the issue is opened or reopened, or when an edit changes the issue body; an edit that changes only the title starts no run. It downloads the archive (HTTPS only, at most 16 MiB), verifies its signature, generates the entry with `xila-package registry entry`, runs `tools/validate.sh`, and opens the pull request. The pull request runs the same validation, including the immutability check.

The workflow merges the pull request automatically only when the developer key already exists and the submission adds no key and no namespace file, the namespace and kind grants of the key cover the package, the version is new, validation passes, and the archive is a GitHub release asset of the repository that the signed package names in `metadata.source`; every other submission waits for a maintainer review. An automatic submission that finds an open review pull request of the same repository on the same submission branch closes it with a comment, deletes the branch with a lease on the commit it read, and continues.

Two hardening rules apply to the workflow itself. The job that proposes a pull request commits only the expected file paths on the commit that the preparation validated, and runs `xila-package registry check` (without `--archives`) on the final tree before it records the `required` status or merges, so the job holding the write token checks the content it proposes. Only one proposal runs at a time per submission branch, while submissions of different versions queue in parallel. And every job that runs the `xila-package` binary (validate, prepare, propose and publish) first verifies it against the SHA-256 digest committed in `tools/xila-package.sh`; only the final binary is cached, never the build directory, and the binary is built as a static musl executable with remapped paths on a pinned runner image and pinned Rust, so the digest does not drift. A cache entry planted by a compromised run therefore fails the job before the binary executes.

After the merge, the publish workflow signs every entry, developer key, namespace file and the index with the repository key (the thick arrow) and deploys the signed site to registry.xila.dev.

## Verify the result

Validation checks entry placement, publisher authorization, and every archive's signature, hash and metadata. The registry's `tools/validate.sh` downloads each entry's archive itself, with curl, into a temporary directory where each file is named after its URL: HTTPS only, including redirects, at most 5 redirects, 16 MiB (`--max-filesize 16777216`) and 120 seconds (`--max-time 120`) per download, with 3 retries. It then runs `xila-package registry check <root> --archives <directory>`, which does not download anything: it verifies each downloaded archive against its entry, checking the size and SHA-256, the signed manifest with the publisher's public key, and the fields the entry copied from that manifest. An archive replaced after publication therefore no longer matches its entry. The pull request runs the same registry validation.
